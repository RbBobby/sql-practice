# Задания по SQL для подготовки к собеседованию

Работай в базе `interview_lab`. Условия и схема — в README. Решения находятся отдельно в `РЕШЕНИЯ.sql`. Во всех результатах явно задавай ORDER BY, если важен порядок. Если иной порядок не указан, сортируй по ID.

## Блок А. Понять таблицы и связи

**1. Ключи и кардинальность — устно, затем посмотреть структуру.**
Найди PK и FK у `films`, `categories`, `film_categories`. Почему PK в связующей таблице состоит из двух столбцов? Может ли один фильм относиться к двум категориям? Может ли категория не иметь фильмов? Можно ли сделать JOIN без FK? Обязателен ли PK для создания таблицы? Чем отличается ключ от индекса?

**2. SELECT, WHERE, ORDER BY.**
Выведи `film_id, title, rating` для фильмов, вышедших с 2023 года включительно и имеющих рейтинг не ниже 8. Сортируй по рейтингу по убыванию, затем по ID.

**3. NULL.**
Найди фильмы без рейтинга. Затем выведи для всех фильмов `film_id, title, rating_label`: текст рейтинга либо «Нет оценки». Почему `rating = NULL` не подходит? Почему замена NULL на 0 может исказить средний рейтинг?

**4. INNER JOIN, связь многие ко многим.**
Выведи `film_id, title, category_id, category_name` для каждой связи фильма с категорией. Фильмы без категории не включай. Сортируй по film_id, category_id. Объясни, почему строк больше, чем фильмов.

**5. LEFT JOIN.**
Сделай тот же отчёт, но сохрани фильмы без категории; у них category_id и category_name должны быть NULL. Какой фильм добавился? Сколько строк получилось?

**6. Поиск отсутствующей связи двумя способами.**
Найди категории без фильмов: сначала через LEFT JOIN и IS NULL, затем через NOT EXISTS. Вывод: `category_id, name`. Почему при проверке отсутствия надёжно использовать ненулевой ключ присоединяемой строки?

**7. Остальные JOIN.**
Перепиши № 5 с RIGHT JOIN. Затем соедини категории с фильмами через таблицу связей так, чтобы сохранить и пустые категории, и фильмы без категорий (FULL JOIN). Вывод: `category_id, category_name, film_id, title`; сортировка по category_id NULLS LAST, film_id. Наконец, построй CROSS JOIN всех категорий со всеми актёрами и предскажи число строк до запуска. Объясни разницу между всеми четырьмя результатами: № 4, № 5, FULL и CROSS.

## Блок Б. Главная задача интервью и её ловушки

**8. Повтор задачи с собеседования.**
Выведи ровно две колонки: `category_name, film_count`. Покажи **все категории**, в том числе с нулём фильмов. Сортируй по category_id. Расскажи, какая таблица должна быть слева, зачем GROUP BY и что именно считает COUNT. Можно ли здесь обойтись без присоединения `films`?

**9. COUNT(*) против COUNT(column).**
Для каждой категории одновременно выведи `category_id, name, row_count, film_count`. Первую величину считай COUNT(*), вторую COUNT(fc.film_id) после LEFT JOIN. Объясни отличие на пустых категориях.

**10. Условие в ON против WHERE.**
Для каждой категории посчитай только фильмы 2024 года. Вывод: `category_name, film_count`; нулевые категории должны остаться. Сначала попробуй фильтр в WHERE, затем исправь. При двух LEFT JOIN какой столбец нужно передать COUNT, чтобы старые фильмы не попали в счётчик?

**11. GROUP BY и HAVING.**
Выведи `category_name, film_count` только для категорий с двумя или более фильмами, по category_id. Почему условие на COUNT нельзя просто поместить в WHERE?

**12. AVG, MIN, MAX, SUM.**
Для каждой категории выведи `category_name, avg_duration, min_duration, max_duration, total_duration`. Среднюю длительность округли до двух знаков. Для пустой категории среднее, минимум и максимум оставь NULL, сумму выведи как 0. Сортировка по category_id.

**13. Размножение строк после нескольких JOIN.**
Для каждого фильма покажи `film_id, title, category_count, actor_count`, сохранив фильмы без связей. В первой попытке присоедини обе связующие таблицы и посчитай обычным COUNT. Почему для «Орбиты» получились неверные числа? Исправь запрос. Назови альтернативу COUNT(DISTINCT ...).

**14. Подзапрос.**
Найди `film_id, title, rating` фильмов с рейтингом строго выше среднего рейтинга всех фильмов. Объясни, как NULL влияет на AVG.

## Блок В. SQL для QA: платежи и подписки

Правила: дата проверки `DATE '2025-02-15'`, период `[starts_at, ends_at)`. В № 16 суммы считаются по всем строкам success, включая намеренный дубль; № 18 отдельно обнаруживает его.

**15. Три таблицы.**
Покажи все подписки: `subscription_id, user_name, plan_name, status, starts_at, ends_at`. Присоедини пользователей и тарифы. Одна строка на подписку.

**16. Успешные оплаты каждого пользователя.**
Выведи `user_id, name, success_count, total_paid`. Включи пользователей без подписок, без платежей и с одними неуспешными платежами. У них должны быть 0 и 0. Не учитывай failed и pending. Объясни, почему это ещё не достоверная финансовая выручка.

**17. Активная подписка без успешной оплаты.**
Найди `subscription_id, user_id` подписок со статусом active, действующих на дату проверки, по которым нет ни одной success-оплаты. Учитывай случаи «платежей совсем нет» и «есть только pending». Прими для упражнения правило: у каждой действующей подписки должна быть хотя бы одна успешная оплата, триала нет.

**18. Дубликаты события.**
Найди `external_id, duplicate_count` для повторяющихся external_id. Выведи также сами строки платежей, относящиеся к найденным дубликатам. Какое ограничение предотвратит такую ошибку, если external_id по контракту глобально уникален? Почему добавление ограничения сейчас не пройдёт?

**19. Пересечение подписок.**
Найди пары разных подписок одного пользователя с одинаковым тарифом и статусом active у обеих, чьи интервалы пересекаются. Вывод: `user_id, first_id, second_id`. Не выдавай пару дважды и не соединяй подписку с самой собой. Если одна заканчивается в день начала другой — это не пересечение. Для упражнения такие пересечения запрещены бизнес-правилом. Здесь ищем пересечения всех сохранённых интервалов, независимо от даты проверки.

**20. Оконная функция.**
Для каждого пользователя покажи последнюю попытку оплаты: `user_id, name, payment_id, status, paid_at`. При одинаковом времени выбирай больший payment_id. У пользователей без платежей значения оплаты должны быть NULL. Используй ROW_NUMBER и CTE; не делай LIMIT 1 на всю таблицу.

## Блок Г. Изменения данных и ограничения

**21. Транзакция и UPDATE.**
Выполни BEGIN, поменяй подписку № 5 с active на cancelled, проверь изменение SELECT, выполни ROLLBACK и снова проверь статус. Что произойдёт при COMMIT вместо ROLLBACK? Почему забытый WHERE опасен?

**22. INSERT и DELETE.**
В одной транзакции добавь категорию с ID 99 «Учебная», свяжи с фильмом № 7, проверь JOIN. Удали сначала связь, затем категорию, выполни ROLLBACK. Почему удаление родителя с существующей связью здесь не разрешено?

**23. Негативные проверки ограничений.**
В независимых транзакциях попробуй: (а) вставить повторную пару (film_id=1, category_id=1); (б) добавить пару (999,1); (в) вставить платёж с amount=-1 для существующей подписки. Предскажи нарушения PRIMARY KEY, FOREIGN KEY и CHECK. После каждой ошибки сделай ROLLBACK. После ошибки PostgreSQL не продолжает обычные запросы внутри этой транзакции до её отката (или отката к SAVEPOINT).

**24. Индекс и план запроса — дополнительное.**
Посмотри EXPLAIN (ANALYZE, BUFFERS) для отбора платежей по subscription_id = 2. В транзакции добавь индекс на subscription_id и сравни план. Заверши ROLLBACK. Почему на семи строках сервер может предпочесть Seq Scan? Создаёт ли FK автоматически индекс на ссылающемся столбце? Какие индексы появляются при PK/UNIQUE? Помни: EXPLAIN ANALYZE реально выполняет запрос.
